对 junqi_engine 做了一次方案层 + 代码层的全面审查。核心结论（供后续修复优先级参考）：

### 致命级（会导致训练完全无效）
1. `junqi/train_rl.py:1162/1174/1179` 热启动分支 `net = JunqiNet.load_from_file(...)` 重新绑定 `net`，
   但 `optimizer` 在 `:1114` 已绑定旧 net → 优化器与新网络脱钩，首轮起权重零更新。

2. `junqi/train_rl.py:1217` `torch.load(opp_path)` 取到的是 `net.save()` 的包装字典

   → 键全不匹配、静默通过 → **自博弈 "best 对手" 是随机初始化网络**（OPP_MIX 约 25% 对局）。

## 第十批（同日）：专家引擎"提升空间"实测诊断（未改任何库文件）

用户问"目前专家引擎（传统搜索引擎）还有提升空间吗"。写了 3 个插桩探针
（`scratch/probe_search_headroom.py`、`probe_depth_sensitivity.py`、`probe_qsearch_cost.py`，
输出 `scratch/probe{,2,3}_out.txt`），全部只做 monkeypatch 计数，**未改 `junqi/` 下任何文件**。

**实测结论（三大块）**：

1. **树内翻棋 99.5% 不搜索**（`search.py:485` 的 `depth <= 1 or ply_depth >= 1` 截断）。
   处女局面：根节点真实展开仅 8 个（d=2）/ 16 个（d=3）chance 节点，其余 1544 / 3080 全走
   静态期望；中盘 98.7%、中后盘 97.9%。
2. **深度参数在暗子密集局面完全无效**：4 个种子（42/101/2026/777）的处女局面，
   depth=2/3/4 的 **best 动作与分值逐位相同**（`翻(3,0)` / 7.64），耗时 1.5s→3.0s→4.5s，
   `evaluate_expert` 调用 36672→73152→109632 线性增长 → **纯浪费**。
   对照组（30 手、25 个暗子）动作也没变，只有分值变（122.88→146.99）。
   ⇒ **"把默认 depth 从 2 调高"不是提升空间，是烧 CPU。**
3. **QSearch 是残局黑洞**：残局（90 手、quiet=0）`qnodes/nodes = 43~47×`，
   depth=2 单步 4.6~6.0s；depth=3 达 33.3s。`_qsearch` 无置换表、只生成吃子动作。

**一个疑似"免费提速"（待 A/B 定论）**：残局 depth=3 时 `qsearch_depth=4` 与 `=16`
决策+分值逐位相同（`走(0,2)->(0,1)` / 57.18），耗时 **33.3s → 8.5s（约 3.9×）**；
但 depth=2 时 qd=4 与 qd=16 决策**不同**（`走(8,1)->(8,2)` vs `走(10,4)->(9,3)`）
⇒ 少数局面外推不可靠，必须对局级 A/B 才能定论。

**其他代码事实（未实测）**：无 aspiration window / LMR / null-move；killer/history 只覆盖
move 不覆盖 flip（而 flip 是暗棋主要动作）；根节点无 aspiration、全窗口；`avoid` 用 -150
硬扣（而分值量级只有几十~几百）；C++ 内核 `junqi_core` 2.7ms/步仍未接入
`ExpertSearchEngine`（~130ms/步）。

**测量层是优先级最高的一块**（承接第九批"degraded 无消费者"）：官方口径 88-92% 和棋、
裁决判分未通过校准（镜像 0.600 > 已知更强方 0.575）⇒ **在测量修好前，"引擎变强"不可证**。
